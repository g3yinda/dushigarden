## M1 子任务

| ID | 内容 | 验收对象 |
|---|---|---|
| D01 | 游戏大厅、朋友房、开局桌面、结算 | 入口连贯，可理解房间与游戏的关系 |
| D02 | 七种功能牌、炸弹、五种普通猫和统一牌背 | 13 种牌面 + 1 种牌背，名称与效果对应 |
| D03 | 选牌、详情、组合、选目标、索要、预知、拆弹、插回、否定、断线状态 | 对照规则逐页走查 |
| D04 | 选牌/出牌/抽牌/攻击/否定/拆弹/洗牌/预知/出局动效 | 动画表达结果，保留清晰文案 |
| D05 | 资产规范、原图与提示词、导出约定、可读性验证 | 名称、尺寸、类型、权利来源可追溯 |

牌面数量以牌库表为准：炸弹、拆弹、攻击、跳过、索要、洗牌、预知、否定共 8 种，另有 5 种普通猫，合计 **13 种牌面 + 1 种牌背**。不可把“普通猫牌”只算一个牌面。不同官方插画版本无需全部重做，首版同功能复用原创图案即可。

## M3 子任务与测试顺序

R01 卡牌目录/规则配置 → R02 2–5 人洗牌发牌 → R03 普通回合/抽牌/胜负 → R04 爆炸/拆弹/插回 → R05 跳过/攻击负债 → R06 洗牌/预知 → R07 索要/组合 → R08 否定窗口及并发版本 → R09 超时/恢复 → R10 公私视图。

每项先根据行为案例写有价值的测试，覆盖输入、结果与可见性；不测试内部函数名或动画样式。随机相关测试用受控随机源验证结果与守恒，生产随机源独立。

## M4 子任务与完成条件

N01 身份与会话 → N02 房间席位和准备 → N03 并发开始 → N04 命令唯一标识与服务端事件序号 → N05 长连接心跳 → N06 状态快照与重连 → N07 服务器定时器 → N08 托管/退出 → N09 服务重启恢复 → N10 操作日志和错误定位。

验证需要多个独立身份；开发工具中开两个窗口不能替代 2–5 台真实设备验收。多账号登录、微信分享和发布能力依赖 M2 的真实账号条件。

## M5 动效实施边界

先实现可操作状态与准确文案，再接入 GPT 生图确认后的原创素材；逐个加入动效并验证时钟。生图是静态图片，不能代替实际交互。设计阶段已按用户原始 Demo 要求制作本地可播放样片，不依赖 Canva；样片完成不代表 M5 游戏动画已实现。

动画中收到新权威状态时，取消或跳过过期展示；不可因动画重复发送操作。图片/图形与文字分层，动态牌数、目标昵称、倒计时必须由界面绘制。

## 版本维护与后续小游戏

用户提供 GitHub 后：建立主分支、功能分支和 PR；文档更改与规则测试同版本提交。里程碑通过时打可回退标签。生成提示词、原图与资产清单、规则版本和变更记录存仓库，密钥及私人对局数据不入库。

新增游戏复用身份、房间、邀请、重连和结果框架，新增独立规则模块与专属桌面；不要为尚未确定的游戏提前开发复杂扩展框架。

## 每个评审节点需要的决定

M0：确认当前规则基准、组合牌启用、线上计时/托管。
M1：确认页面布局、牌面识别、动画强度和美术方向。
M2：确认微信发布载体、后端预算/账号、GitHub 地址。
M6：确认朋友试玩通过，允许开始发布流程。
